# Security model

OpenWarp stores credentials and secret material. Deployment choices, access policy, and key custody are part of its security model. The implementation has automated security tests, but those tests are not an independent security or cryptography audit.

## Choose an encryption mode

| Property | Server-side encryption (SSE) | End-to-end encryption (E2E) |
| --- | --- | --- |
| Environment key | Generated and used by the server | Generated by the client for a true E2E environment |
| Stored key material | Environment key wrapped by the instance master key | Environment key wrapped for each authorised user's public key |
| Plaintext processing | Server decrypts for reads, exports, and integrations | Client decrypts locally |
| Normal CLI `run` and provider sync | Available subject to access policy | Not the normal SSE workflow; use the E2E commands |
| Recovery requirements | Database and matching master key | Database and the user's original private key, or another authorised key holder who can grant access |

SSE is the default. A per-environment key encrypts secret names, values, comments, and integration configuration. The instance master key wraps these environment keys. A server operator with the database and master key can decrypt SSE secrets.

For true E2E creation, the client must supply `wrapped_key` to the E2E creation endpoint. The compatibility path that omits it lets the server generate a key and returns `server_generated: true`. That path does not keep the key unknown to the server. Prefer the CLI's `e2e-create` command.

Browser E2E decryption uses the JavaScript implementation in [`e2e.js`](../crates/server/src/e2e.js). The recovery kit stays in the page during this workflow. The browser still downloads code from the server, so a compromised server that serves altered JavaScript is a separate threat. Local decryption does not eliminate the need to trust the delivered client.

## Key custody and recovery

| Material | What it protects | Where to keep a recovery copy |
| --- | --- | --- |
| `OPENWARP_MASTER_KEY` | SSE environment keys and server-managed encrypted state | An independent secret store, separate from database backups |
| User recovery kit | The user's X25519 private key and E2E access | An offline or securely backed-up user secret store |
| Database backup | Ciphertext, accounts, wrapped keys, policies, and history | Encrypted backup storage with restricted access |
| Deployment secrets | Database credentials, provider sign-in credentials, email relay token | Your deployment secret store |

The master key is exactly 32 random bytes encoded in base64. Production startup requires it. Development can generate a key and save it in the database's `meta` table. In that mode, copying the database also copies the key needed to decrypt SSE data.

Do not replace the master key for an existing database with a newly generated one. The setting is not a key-rotation operation: existing wrapped keys still require the original key. When promoting a development database, preserve its existing key.

Password reset with a recovery kit re-wraps the same private key under the new password. The explicit `discard_e2e_key` alternative creates a different key pair; existing E2E grants to the old key become unreadable to that account. Reset revokes the account's sessions and OAuth credentials. An instance master key does not recover a lost client-held E2E private key.

## Cryptographic building blocks

The [`openwarp-crypto` crate](../crates/crypto/src/lib.rs) implements X25519 key exchange, XChaCha20-Poly1305 authenticated encryption, Argon2id password-based key wrapping, and token hashing. GitHub secret sync uses a libsodium-compatible sealed-box format. Algorithm selection alone is not proof that the surrounding protocols or implementations are secure.

Secret metadata is not uniformly encrypted. Identifiers, membership, paths, tags, timestamps, audit records, and operational state can reveal information. Treat the entire database as sensitive, including when secret values are ciphertext.

## Password reuse detection

When a standard `secret` value is written, the server stores a fingerprint in `secrets.value_fp`, keyed and salted with the workspace id. The fingerprint is HMAC-SHA256 under a key derived from the instance master key, not a plain hash of the value. Equal values in two workspaces do not produce equal fingerprints. A database-only compromise therefore cannot test a candidate password list against the stored fingerprints. The fingerprint is not reversible: the master key lets an attacker test guesses, not recover a value directly.

The console checks a value before staging a new secret, an edit, or an import. It reports occurrences in the same workspace and only in environments the caller can already open. An environment-scoped token cannot use the check to see other environments. Sealed values are never indexed, so a match cannot confirm a sealed value the caller cannot read. `config` and `ssh_key` values are not indexed, and E2E environments are skipped because the server never sees their plaintext.

Both `orgs.reuse_check` and `apps.reuse_check` default to on, and the warning requires both. Turning a switch off suppresses the warning but does not delete existing fingerprints. Existing rows are indexed by a one-time backfill at startup; new writes are indexed inline. The check is advisory, so an authorised caller can save the value anyway. Do not treat a missing warning as proof that a value is unique.

## Identity and authentication

- Password sign-in uses an account session. Browser sessions use the HttpOnly `ow_session` cookie; HTTPS public URLs or `OPENWARP_SECURE_COOKIES=1` enable its Secure flag.
- Password signup requires a verified email address before any session is issued. Emails asserted by a configured identity provider (Google, GitHub, Apple, OpenAI, Microsoft Entra, Okta, Auth0, GitLab, Slack, Salesforce, Atlassian, X, custom OIDC, workspace OIDC, SAML, SCIM, or an accepted invite) are treated as verified; a provider-asserted email never silently links to an existing password account.
- TOTP multi-factor authentication adds a challenge and recovery codes. Store recovery codes separately from the device that generates TOTP codes.
- Google, GitHub, Apple, OpenAI, Microsoft Entra, Okta, Auth0, GitLab, Slack, Salesforce, Atlassian, X and custom OIDC sign-in require configured provider credentials. They are not advertised when unconfigured. Apple posts its authorization response and authenticates with a signed client-secret JWT; OpenAI, Microsoft, Okta, Auth0, GitLab, Salesforce, Atlassian, X and custom OIDC use PKCE where the provider supports it. A custom provider authenticates the client secret with the method discovery advertises (POST by default, HTTP Basic when that is the only supported method) and accepts RS, PS and ES `id_token` signatures only.
- Microsoft accepts the tenant-specific issuer from the token's `tid` claim and treats `preferred_username` or `upn` as the address when Entra omits `email`. X requires the `users.email` scope and uses only the `confirmed_email` field, failing closed when it is absent.
- Custom OIDC identities bind by issuer and subject, so changing `OPENWARP_OIDC_ISSUER` does not inherit bindings made under the previous issuer. The issuer and every discovered or configured endpoint pass the egress policy before a request is made.
- Workspace OIDC binds identities by issuer and subject. A matching email address alone does not authorise silent linking to an existing password account.
- CLI browser login uses OAuth with PKCE. OAuth scopes narrow what a client can do; workspace and environment policy still applies.
- Service tokens can be scoped and revoked. Machine identities use Universal Auth and issue short-lived tokens. Prefer these over human credentials for automation.

The first verified account is the instance owner. Bootstrap the instance on a restricted network, register that account, open the verification link, then set the signup policy before public exposure.

## Authorisation boundaries

The console calls an organisation a workspace. Workspace membership is the outer access boundary. Applications and environments sit inside it.

| Control | Meaning |
| --- | --- |
| Managed owner/admin roles | Broad workspace administration |
| Managed developer role | Broad secret and automation permissions, not a read-only role |
| Custom role | Only its stored permissions; unspecified permissions are denied |
| Application/environment grants | Scope membership where supported |
| Restricted environment | Explicit application or environment access is required, with owner/admin exceptions |
| Approval-required environment | Non-admin direct writes are restricted; use proposals |
| Environment-scoped token | Cannot be used as an unrestricted cross-environment token |

Review custom roles against the actions callers need. An approved access request and the `restricted` flag are separate concepts; granting temporary access does not by itself make an otherwise open environment exclusive.

SCIM requests require workspace context through `org_id` and administrative authority. Deactivation removes membership in that workspace rather than treating a tenant administrator as an instance-wide account administrator.

## Device certificates

Device certificates are client certificates for an external broker. OpenWarp does not terminate mTLS with them and does not treat a device certificate as a workspace credential; the broker is the relying party.

Device enrollment consumes a one-time code and a PKCS#10 CSR. The server verifies the CSR self-signature, ignores its subject, SAN and extension requests, and issues a certificate for the device record's name and SANs with the CSR's public key. The device private key never reaches the server on this path. The older `POST /api/pki/cas/:id/issue` path still generates a key on the server and returns it once; it requires workspace admin and exists for devices that cannot produce a CSR.

Enrollment codes are 256-bit random values. Only a SHA-256 hash is stored, the code is consumed atomically on first use, and it expires between five minutes and seven days. Treat a code as a credential: anyone holding it can obtain one certificate for that device until it is used or expires. Mint codes per device, not per fleet, and delete the device record when the code is no longer needed.

CN and SANs are taken from the device record, never from the CSR, so one enrolled device cannot claim another device's identity. Device certificates are client-auth only and default to 90 days. Issuing a new certificate moves the device's active pointer but does not revoke the previous one, so revoke it explicitly when the old key may be compromised. Prefer a dedicated CA per fleet or environment: the CA private key is encrypted with the instance master key, so an attacker with the database and master key can forge any certificate under that CA. Replacing the CA is the rotation boundary; existing broker trust must be updated deliberately.

The CRL and OCSP endpoints are public. A CRL is a signed public artifact and brokers fetch it without credentials; it reveals the serial numbers and revocation state of that CA's certificates. CA identifiers are random and not enumerable. Revocation times come from the stored `revoked_at` value, and the CRL's `nextUpdate` is seven days, so short-lived certificates are the more reliable revocation mechanism for a fleet.

## Network and operational controls

Workspace IP allowlists protect authenticated API, MCP, and SCIM access. They are not a replacement for a firewall: authentication/bootstrap routes have different handling. Keep the server and database on trusted networks and expose only the intended HTTPS entry point.

Only enable forwarded-IP trust behind a proxy you control. Set `OPENWARP_TRUSTED_PROXIES` to the actual proxy peers; a broad trusted range can weaken IP-based controls.

The current PostgreSQL driver uses `postgres::NoTls`. Do not assume an external database connection is encrypted because the console uses HTTPS. Use an isolated network or a separately configured encrypted transport, and test the deployment's requirements.

Provider integrations receive plaintext SSE values. Their credentials, destination URLs, permissions, and remote retention policy are part of your trust boundary. Integration sync excludes sealed values and user-specific overrides. Do not treat sealed secrets as a mechanism for delivering values to providers.

Log streams, email relays, OIDC endpoints, and generic webhooks are outbound connections. Apply network egress controls as well as application validation. Allowing private egress intentionally broadens the destinations the server can contact. See [configuration](CONFIGURATION.md).

## Secret handling on clients

The CLI attempts to store access and refresh tokens in the operating system credential store. If that is unavailable, it can fall back to its configuration file. Unix file permissions are restricted; other platforms need their own access controls. `OPENWARP_NO_KEYRING=1` explicitly selects file storage.

`get`, `secrets --show`, exports, and child-process injection expose plaintext to the local user and process. Avoid terminal recordings, shared CI logs, checked-in export files, and command-line arguments containing real secrets. Environment variables are not a protection from a compromised child process or privileged local account.

Lockbox shares are intended for one-time viewing. Anyone with the complete link can attempt to consume it. Treat the URL fragment containing the decryption key as secret material; do not send the link through a system that rewrites or previews sensitive links without testing that behavior.

## Before production use

1. Obtain an independent review appropriate to the data you will store.
2. Set the public HTTPS URL, external master key, and production mode.
3. Bootstrap the instance owner privately; choose signup and invitation policies.
4. Verify database transport, proxy trust, provider egress, and least-privilege tokens.
5. Rehearse restoration with the original master key and an E2E user's recovery kit.
6. Check that logs and metrics do not enter less trusted systems than your secrets.

Do not publish live credentials or exploit details in a public issue. Use a private reporting channel agreed with the maintainer; this repository does not establish a dedicated security contact in this guide.
