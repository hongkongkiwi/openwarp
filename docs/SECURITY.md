# Security model

OpenWarp stores credentials and secret material. Deployment choices, access policy, and key custody are part of its security model. The implementation has automated security tests, but those tests are not an independent security or cryptography audit.

## Choose an encryption mode

| Property | Server-side encryption (SSE) | End-to-end encryption (E2E) |
| --- | --- | --- |
| Environment key | Generated and used by the server | Generated by the client for a true E2E environment |
| Stored key material | Environment key wrapped by the instance master key | Environment key wrapped for each authorised user's public key |
| Plaintext processing | Server decrypts for reads, exports, and integrations | Client decrypts locally |
| Normal CLI `run` and provider sync | Available subject to access policy | Not the normal SSE workflow; use the E2E commands |
| Recovery requirements | Database and matching master key | Database and the user's original private key, or another authorised key holder who can grant access |

SSE is the default. A per-environment key encrypts secret names, values, comments, paths, tags, and integration configuration, with associated data binding each ciphertext to its record. The instance master key wraps these environment keys; with a KMS configured, the root and environment keys are wrapped externally instead. A server operator with the database and master key can decrypt SSE secrets.

The [encryption modes and key custody](ENCRYPTION.md) page adds the delegated mode, the KMS bridge contract, the metadata and runner boundaries, and the client-derived auth caveats.

For true E2E creation, the client must supply `wrapped_key` to the E2E creation endpoint. The compatibility path that omits it lets the server generate a key and returns `server_generated: true`. That path does not keep the key unknown to the server. Prefer the CLI's `e2e-create` command.

Browser E2E decryption uses the JavaScript implementation in [`e2e.js`](../crates/server/src/e2e.js). The recovery kit stays in the page during this workflow. The browser still downloads code from the server, so a compromised server that serves altered JavaScript is a separate threat. Local decryption does not eliminate the need to trust the delivered client.

## Key custody and recovery

| Material | What it protects | Where to keep a recovery copy |
| --- | --- | --- |
| `OPENWARP_MASTER_KEY` | SSE environment keys and server-managed encrypted state | An independent secret store, separate from database backups |
| User recovery kit | The user's X25519 private key and E2E access | An offline or securely backed-up user secret store |
| Database backup | Ciphertext, accounts, wrapped keys, policies, and history | Encrypted backup storage with restricted access |
| Deployment secrets | Database credentials, provider sign-in credentials, email relay token | Your deployment secret store |

The master key is exactly 32 random bytes encoded in base64. Production startup requires it. Development can generate a key and save it in the database's `meta` table. In that mode, copying the database also copies the key needed to decrypt SSE data.

Do not replace the master key for an existing database with a newly generated one. The setting is not a key-rotation operation: existing wrapped keys still require the original key. When promoting a development database, preserve its existing key.

Password reset with a recovery kit re-wraps the same private key under the new password. The explicit `discard_e2e_key` alternative creates a different key pair; existing E2E grants to the old key become unreadable to that account. Reset revokes the account's sessions and OAuth credentials. An instance master key does not recover a lost client-held E2E private key.

## Cryptographic building blocks

The [`openwarp-crypto` crate](../crates/crypto/src/lib.rs) implements X25519 key exchange, XChaCha20-Poly1305 authenticated encryption, Argon2id password-based key wrapping, and token hashing. GitHub secret sync uses a libsodium-compatible sealed-box format. Algorithm selection alone is not proof that the surrounding protocols or implementations are secure.

Secret metadata is not uniformly encrypted. Identifiers, membership, paths, tags, timestamps, audit records, and operational state can reveal information. Treat the entire database as sensitive, including when secret values are ciphertext.

## Audit chain and wrapping tokens

Audit rows carry a per-organisation sequence number, the previous row's hash and a SHA-256 hash over the row's fields. `GET /api/orgs/:id/audit/verify` recomputes the chain and reports the first broken link. The chain is tamper-evident, not tamper-proof: an operator with database write access can rewrite rows and recompute an edited prefix, and rows written before migration 17 are unchained. Forward audit events to an independent log stream when the trail must survive the database.

`POST /api/envs/:id/wrap` returns a single-use `owwrap_...` Bearer token that another party can redeem once at `POST /api/unwrap`. The payload is encrypted under the environment key, excludes sealed values, and expires after 60 to 86400 seconds. `GET /api/unwrap` looks the token up without consuming it. The token is not a session or service token and cannot call any other route. Anyone who obtains it can redeem it once, so deliver it over TLS and treat it as the secret it carries. Unwrapping is authorised by the token alone, so an organisation IP allowlist is not consulted on that route.

## Password reuse detection

When a standard `secret` value is written, the server stores a fingerprint in `secrets.value_fp`, keyed and salted with the workspace id. The fingerprint is HMAC-SHA256 under a key derived from the instance master key, not a plain hash of the value. Equal values in two workspaces do not produce equal fingerprints. A database-only compromise therefore cannot test a candidate password list against the stored fingerprints. The fingerprint is not reversible: the master key lets an attacker test guesses, not recover a value directly.

The console checks a value before staging a new secret, an edit, or an import. It reports occurrences in the same workspace and only in environments the caller can already open. An environment-scoped token cannot use the check to see other environments. Sealed values are never indexed, so a match cannot confirm a sealed value the caller cannot read. `config` and `ssh_key` values are not indexed, and E2E environments are skipped because the server never sees their plaintext.

Both `orgs.reuse_check` and `apps.reuse_check` default to on, and the warning requires both. Turning a switch off suppresses the warning but does not delete existing fingerprints. Existing rows are indexed by a one-time backfill at startup; new writes are indexed inline. The check is advisory, so an authorised caller can save the value anyway. Do not treat a missing warning as proof that a value is unique.

## Identity and authentication

- Password sign-in uses an account session. Browser sessions use the HttpOnly `ow_session` cookie; HTTPS public URLs or `OPENWARP_SECURE_COOKIES=1` enable its Secure flag.
- Password signup requires a verified email address before any session is issued. Emails asserted by a configured identity provider (Google, GitHub, Apple, OpenAI, Microsoft Entra, Okta, Auth0, GitLab, Slack, Salesforce, Atlassian, X, Discord, LinkedIn, WorkOS, custom OIDC, workspace OIDC, SAML, SCIM, or an accepted invite) are treated as verified; a provider-asserted email never silently links to an existing password account.
- TOTP multi-factor authentication adds a challenge and recovery codes. Store recovery codes separately from the device that generates TOTP codes.
- Google, GitHub, Apple, OpenAI, Microsoft Entra, Okta, Auth0, GitLab, Slack, Salesforce, Atlassian, X, Discord, LinkedIn, WorkOS and custom OIDC sign-in require configured provider credentials. They are not advertised when unconfigured. Apple posts its authorization response and authenticates with a signed client-secret JWT; OpenAI, Microsoft, Okta, Auth0, GitLab, Salesforce, Atlassian, X and custom OIDC use PKCE where the provider supports it. A custom provider authenticates the client secret with the method discovery advertises (POST by default, HTTP Basic when that is the only supported method) and accepts RS, PS and ES `id_token` signatures only.
- Microsoft accepts the tenant-specific issuer from the token's `tid` claim and treats `preferred_username` or `upn` as the address when Entra omits `email`. X requires the `users.email` scope and uses only the `confirmed_email` field, failing closed when it is absent.
- Custom OIDC identities bind by issuer and subject, so changing `OPENWARP_OIDC_ISSUER` does not inherit bindings made under the previous issuer. The issuer and every discovered or configured endpoint pass the egress policy before a request is made.
- Workspace OIDC binds identities by issuer and subject. A matching email address alone does not authorise silent linking to an existing password account.
- Social sign-in binds each expiring, single-use state to an independent random HttpOnly browser cookie. The cookie secret never enters the authorization URL; the database stores an HMAC of the public state keyed by that secret. Callbacks must present the initiating flow's cookie before consuming state or contacting the provider. Separate cookie names allow concurrent flows. HTTPS Apple callbacks use `SameSite=None; Secure` for cross-site form POSTs; other flows use `SameSite=Lax`. Local HTTP fixtures use Lax cookies and do not model Apple's cross-site browser POST behavior.
- CLI browser login uses OAuth with PKCE. OAuth scopes narrow what a client can do; workspace and environment policy still applies.
- Service tokens can be scoped and revoked. Machine identities use Universal Auth and issue short-lived tokens. Prefer these over human credentials for automation.

The first verified account is the instance owner. Bootstrap the instance on a restricted network, register that account, open the verification link, then set the signup policy before public exposure.

## Authorisation boundaries

The console calls an organisation a workspace. Workspace membership is the outer access boundary. Applications and environments sit inside it.

| Control | Meaning |
| --- | --- |
| Managed owner/admin roles | Broad workspace administration |
| Managed developer role | Broad secret and automation permissions, not a read-only role |
| Custom role | Only its stored permissions; unspecified permissions are denied |
| Application/environment grants | Scope membership where supported |
| Restricted environment | Explicit application or environment access is required, with owner/admin exceptions |
| Approval-required environment | Non-admin direct writes are restricted; use proposals |
| Environment-scoped token | Cannot be used as an unrestricted cross-environment token |

Review custom roles against the actions callers need. An approved access request and the `restricted` flag are separate concepts; granting temporary access does not by itself make an otherwise open environment exclusive.

SCIM requests require workspace context through `org_id` and administrative authority. Deactivation removes membership in that workspace rather than treating a tenant administrator as an instance-wide account administrator.

## Workspace creation and invitation consent

Workspace creation is an instance-owner policy separate from self-signup. `OPENWARP_WORKSPACE_CREATION` pins it for native and Worker deployments. Disabling it prevents explicit creation and automatic personal workspaces, not invitation acceptance. Policy changes and last-workspace deletion share a database lock row; existing ownership and unresolved-lease checks still apply. An operator can pin creation closed on an empty database, but must reopen it to bootstrap a workspace.

Inviting an existing account does not add membership. `GET /api/auth/invite?token=...` previews only the workspace, email, role, expiry and whether an account exists. It does not return token hashes, passwords or key material. Existing accounts must consent with a matching active, verified account session; a valid session for another account cannot create the invitee on either password protocol. New accounts may redeem a token through legacy or client-derived creation without a personal workspace. Social sign-in may admit an invited address while signup is closed but leaves the invitation unconsumed until explicit acceptance. Workspace-specific directory provisioning retains its separate admission rules.

Invitations expire after seven days. Acceptance consumes the token and inserts membership in one checked database batch; failure rolls both back. Workspace admins list pending invitations by opaque management IDs, revoke them, or resend a rotated token. Resending invalidates the old token. Privileged role grants remain owner-only. Tracked invitations recheck the inviter's current grant authority in the token-consumption transaction, including admin and custom privileged roles. Human inviters must still be active and verified; machine inviters must still exist in the destination workspace. Legacy invitations without an inviter retain their unexpired token/email contract. Preview and acceptance enforce the destination workspace's IP allowlist even before membership exists. Deliver links over trusted channels; possession authorises new-account creation for the named address. The consume-time check does not serialize all membership and role mutations; cross-backend concurrent role-change behavior still needs runtime validation. The policy guards avoid same-table UPDATE subqueries, but this repair has not been exercised against a live MySQL/MariaDB server.

## Account lifecycle and OAuth consent

`DELETE /api/me` accepts only an account session, with no password or email body. Any workspace ownership blocks it, including co-ownership. Issued API keys and unexpired OAuth access-token pairs produce a 409 with counts until the caller repeats with `?confirm=true`. A refusal does not revoke credentials or release instance ownership. Successful deletion removes sessions, OAuth credentials, personal keys, grants, linked identities, passkeys, authentication challenges and MFA state. Issued SSH certificates are marked revoked; hosts must refresh their revocation files to enforce that change. Workspace history retains opaque user IDs.

Workspace owners can delete a workspace using `DELETE /api/orgs/{id}?confirm=true`. Ownership transfer requires an active, verified member. Instance ownership transfer uses `PUT /api/instance/owner` with `user_id` or `email` and requires the current instance owner and an active, verified recipient. An instance owner with no other active, verified account may delete itself once its workspaces are gone. Local deletion batches roll back on database errors, including on Workers. Provider operations are not part of that transaction. Workspace deletion refuses unresolved dynamic leases; revoke issued credentials before deleting their workspace. Lease issuance reserves a local record before contacting a provider. If issuance or final persistence fails ambiguously, that pending record blocks deletion and requires operator reconciliation rather than claiming the remote credential was removed. Copies already delivered to clients or remote secret stores are not erased by deleting local records.

OAuth secret scopes do not authorise membership, settings, audit, token minting, PKI or SCIM administration; those routes require `org:admin` in addition to the caller's existing permissions. `org:admin` does not imply secret access. Scoped service tokens use the same separation; empty service-token scopes retain legacy access. Authorisation accepts only the API issuer or its `/mcp` endpoint as a named resource, defaults an omitted resource to the API, and preserves the resource when refreshing tokens. API and MCP tokens cannot cross audiences. Password consent requires email verification, including the legacy password path; existing client-derived authentication and MFA checks still apply.

## SSH certificate authority

An SSH CA moves part of the trust decision onto the target host: sshd accepts any certificate its `TrustedUserCAKeys` CA signed while the certificate is inside its validity window. OpenWarp therefore does not mediate the login itself, and a host enforces expiry rather than asking the server whether a session is still allowed.

The private key of the subject never reaches the server. The server holds only the CA private key, sealed with the master key in the same column as an X.509 CA, so master-key rotation re-wraps it. Losing the master key without a backup means reissuing the CA and reinstalling it on every host.

The principal, not the signature, is the authorisation boundary. A certificate granted for `root` authenticates as root on every host that trusts the CA, so issuance requires a per-CA role grant that matches the requested principal. Patterns are an exact name, one trailing `*`, or a bare `*`; a bare `*` is owner-only and should be treated as root-equivalent. A CA with no grant issues nothing. Adding a grant for a role you do not intend is equivalent to granting that role shell access to the matching accounts.

Revocation is bounded by what the host has. The KRL and the plain `RevokedKeys` file are both served from the revocation table, but a host only enforces them after it refreshes the file, and a host that is offline keeps honouring a revoked certificate until it expires. Keep lifetimes short. A compromised CA key cannot be contained by revocation at all, only by replacing the CA on every host.

Host certificates carry the same weight in the other direction: a client that trusts the CA for host names will accept any host certificate it signed. That is why host issuance is limited to a hostname and public key an admin registered, and why the registry has no wildcards. Rotating a host key means removing and re-registering the pair; outstanding certificates keep working until they expire, so rotate the registry before the old certificate's lifetime runs out.

A certificate for `root`, or one issued under a bare `*` grant, is root-equivalent on every trusting host, so issuance requires a step-up: an emailed code, plus TOTP when the account has it, exchanged for a single-use `X-OpenWarp-Step-Up` grant. Machine identities cannot satisfy a second factor and are refused privileged principals outright, so a stolen machine token cannot mint a root certificate.

Machine certificates use the same path: a workspace identity signs with its own role, so a token minted for a developer identity cannot request a principal outside that role's grant.

## Network and operational controls

Workspace IP allowlists protect authenticated API, MCP, and SCIM access. They are not a replacement for a firewall: authentication/bootstrap routes have different handling. Keep the server and database on trusted networks and expose only the intended HTTPS entry point.

Only enable forwarded-IP trust behind a proxy you control. Set `OPENWARP_TRUSTED_PROXIES` to the actual proxy peers; a broad trusted range can weaken IP-based controls.

The PostgreSQL driver connects without TLS, and the MySQL/MariaDB driver uses TLS only when the connection URL sets `require_ssl=true`. Do not assume an external database connection is encrypted because the console uses HTTPS. Use an isolated network or a separately configured encrypted transport, and test the deployment's requirements.

Provider integrations receive plaintext SSE values. Their credentials, destination URLs, permissions, and remote retention policy are part of your trust boundary. Integration sync excludes sealed values and user-specific overrides. Do not treat sealed secrets as a mechanism for delivering values to providers.

Log streams, email relays, OIDC endpoints, and generic webhooks are outbound connections. Apply network egress controls as well as application validation. Allowing private egress intentionally broadens the destinations the server can contact. See [configuration](CONFIGURATION.md).

## Secret handling on clients

The CLI attempts to store access and refresh tokens in the operating system credential store. If that is unavailable, it can fall back to its configuration file. Unix file permissions are restricted; other platforms need their own access controls. `OPENWARP_NO_KEYRING=1` explicitly selects file storage.

`get`, `secrets --show`, exports, and child-process injection expose plaintext to the local user and process. Avoid terminal recordings, shared CI logs, checked-in export files, and command-line arguments containing real secrets. Environment variables are not a protection from a compromised child process or privileged local account.

Lockbox shares are intended for one-time viewing. Anyone with the complete link can attempt to consume it. Treat the URL fragment containing the decryption key as secret material; do not send the link through a system that rewrites or previews sensitive links without testing that behavior.

## Before production use

1. Obtain an independent review appropriate to the data you will store.
2. Set the public HTTPS URL, external master key, and production mode.
3. Bootstrap the instance owner privately; choose signup and invitation policies.
4. Verify database transport, proxy trust, provider egress, and least-privilege tokens.
5. Rehearse restoration with the original master key and an E2E user's recovery kit.
6. Check that logs and metrics do not enter less trusted systems than your secrets.

Do not publish live credentials or exploit details in a public issue. Use a private reporting channel agreed with the maintainer; this repository does not establish a dedicated security contact in this guide.
