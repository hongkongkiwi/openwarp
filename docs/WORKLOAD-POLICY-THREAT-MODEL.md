# Workload identity and path policy threat model

## Scope and acceptance

F2 adds JWT workload login, including Kubernetes projected service-account tokens, to existing machine identities. F5 narrows a role's existing permissions to selected secret folders within an SSE environment. Neither mechanism grants permissions absent from existing workspace roles, OAuth scopes, environment grants or token scopes.

## Workload identity

Only a workspace owner can configure a workload trust binding. A binding pins an identity, exact issuer, audience, exact subject and a trusted public JWKS URL. Kubernetes subjects use `system:serviceaccount:<namespace>:<name>` with an explicitly configured cluster issuer and audience. There is no wildcard subject, claim-to-role mapping or email-based account linking. A token cannot choose its issuer, JWKS endpoint, identity role or environment scope.

Accept only asymmetric signing algorithms supported by the configured public key. Require verified issuer, audience, subject, expiry and issuance time. Enforce not-before, bounded clock skew and a maximum assertion lifetime. Reject missing claims, unsigned tokens, symmetric algorithm confusion, unknown signing keys, and tokens whose expiry has passed. Do not use an assertion after its expiry to mint a longer-lived access token. Reject the same assertion on repeated exchange through an atomic persisted claim. A projected Kubernetes token is a bearer credential; a thief who exchanges it first can still act until the resulting short-lived token expires. Require the configured audience as the sole audience, a maximum assertion lifetime of one hour, and an access-token lifetime of at most five minutes or the assertion's remaining lifetime. Permit at most 30 seconds of future issuance-time skew, without extending expiry. Replay protection covers duplicate identity bindings, not just one binding. Derive the replay identity from verified signing input, not signature bytes that can have equivalent valid encodings. Deleting or changing a trust binding invalidates its issued credentials; deleting an identity invalidates every credential for that identity.

Validate configured JWKS destinations and revalidate them on exchange against the egress policy. On the native server, resolve the configured hostname and pin only approved addresses for the request; checking URL text alone does not prevent DNS rebinding. Disable redirects. Bound request time, JWKS response size and assertion/request sizes. Private Kubernetes clusters require the operator's existing private-egress override; workload configuration cannot enable it. Reject workload exchange on Workers until bounded fetch, deadlines and destination enforcement are implemented there. Do not log assertions, service-account credentials or returned tokens.

## Path policy

Policies are owner-managed restrictions keyed by environment and role. No policy retains existing behavior. A configured policy is an allowlist of canonical folder prefixes and explicit read, write and delete actions. Empty rules deny every path. `/team/` includes descendants but not `/team-other/`. Reject noncanonical paths, dot segments, duplicate separators and control characters rather than interpreting alternate representations. Rules never override existing action permissions.

Check resolved stored paths for direct secret-ID operations and target paths for writes. Lists, exports, search, scanning, reuse detection and MCP reads must filter before reference substitution, so an allowed secret cannot interpolate a forbidden value. Base exports are not an escape. Bulk writes must validate all requested paths before the first mutation. History and restore must check historical paths as well as the current path. Personal overrides require write access.

A caller subject to path restrictions must not obtain an environment key, clone a complete environment, create broader tokens or identities, change roles or grants, configure provider sync or rotation, approve proposals, access snapshots or invoke any other unmediated whole-environment operation. Suppress automatic provider synchronization for restricted writes, deletes and restores; do not send a filtered subset to a mirror adapter, which could delete remote secrets outside that subset. Use a fail-closed route allowlist for restricted principals, including MCP tool names. Owners retain policy administration; unrestricted roles retain existing behavior. E2E and delegated environments cannot support a server-enforced plaintext folder policy because the server cannot authenticate client-encrypted metadata independently of the client-held environment key. Reject policy creation for those modes and reject mode transitions that would strand an active policy.

## Other requested features

F6 permits production startup with a configured KMS and no plaintext master-key environment variable. KMS errors, malformed wrapped roots and a missing KMS for an already wrapped database remain fatal. Restart must recover the same root, not generate a replacement. Concurrent first boots must install one root and adopt the persisted winner before either process encrypts records. Remove a development plaintext root only after a valid wrapped copy is stored; retry its removal on later boots. This is auto-unseal through the existing bridge, not Shamir shares or recovery-key support.

F7 rotates existing PostgreSQL login passwords using fixed quoted identifiers and literals, never caller-supplied SQL. Connection targets must pass the database host allowlist using the actual driver configuration, not a string prefix. Stage an encrypted pending password before the remote change, retain recoverable state after uncertain outcomes, and do not report success until local storage matches the remote password. This is a remote/local state transition, not a distributed transaction. Existing E2E and sealed-secret restrictions apply.

F8 renders explicit local templates from authorized SSE exports. Cache secrets only in memory with a bounded lifetime. Fail closed on authentication and authorization errors, never extend stale values during outages, never evaluate shell expressions or execute hooks. Write output atomically with owner-only permissions; reject symlink destinations. Template output is plaintext and remains the operator's responsibility after writing.

F10 provides workspace-scoped transit keys with versioned authenticated encryption, rotation and rewrap. Keys are never returned, and ciphertext binds workspace, key identifier, key version and caller-supplied context. Separate manage, encrypt and decrypt permissions. Reject cross-workspace, cross-key, context-mismatched and malformed ciphertext. Do not log payloads. Transit is server-side encryption and does not claim E2E privacy. Root rotation must retain access to transit keys.

## Verification and review

Independently authored tests must establish missing behavior before implementation, then stay frozen during repair. Exercise wrong tenant, wrong subject/audience/issuer, expired/replayed assertions, denied paths and indirect access surfaces. Review the implemented diff against this model before marking it ready. Mock issuers and bridges demonstrate protocol behavior, not compatibility with a live cloud KMS or Kubernetes cluster. Report native, database and Worker coverage separately.
